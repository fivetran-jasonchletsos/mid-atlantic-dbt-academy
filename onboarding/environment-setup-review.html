Environment Setup Review

Reviewer: Jason Chletsos  ·  New SE: Anthony Bianay  ·  Work through every step in order, on Anthony's machine, with Anthony driving. Check the box only when the pass condition is met.

PART AAccounts and access

1.Fivetran login works

Anthony logs into Fivetran (not you, not a shared screen) and lands on a dashboard he can read.

Pass: he can see the connector list and open a connector's detail page.

If it fails: resolve account/SSO access before anything else — nothing below works without it.

2.dbt Cloud login and IDE access

He logs into dbt Cloud, opens the sandbox project, and launches the Cloud IDE.

Pass: the file tree shows models/, seeds/, macros/, tests/, and dbt_project.yml.

If it fails: he may have a dbt Cloud seat but no access to this project — fix project permissions, not the IDE.

PART BFivetran side: connector and first sync

3.Sandbox connector exists and points at an MDLS destination

Open his connector. Confirm it targets the Managed Data Lake Service destination (S3 + Glue), or the equivalent sandbox destination, and that the destination schema is clearly prefixed with his own name so his sandbox syncs are identifiable in a shared workspace.

Pass: connector card shows the MDLS (or equivalent) destination and a sensible schema name.

4.First sync has completed — and he knows where to verify it

Check sync status in the Fivetran UI together, then open the connector's schema tab. Tell him explicitly: this tab is the ground truth his bronze sources.yml must match 1:1, because bronze does no renaming.

Pass: sync shows complete; he can name the tables that landed.

If it fails: a build against a half-finished sync is the most common live-demo failure — wait for the sync, do not proceed on a partial one.

PART Cdbt Cloud side: environments, Git, and a clean build

5.Development and Deployment environments both exist

Open the project's environment settings. Confirm a Development environment (his IDE session, his own dev schema) and a Deployment environment (what scheduled jobs run against), and that he can say which is which. Demos live and die by knowing which one you're looking at.

Pass: both environments exist and Development targets his own schema, not a shared one.

6.Git works from the IDE

Have him create a scratch branch directly from the Cloud IDE before touching anything. This proves repo write access, not just read.

Pass: branch created and shown as active in the IDE.

7.Bronze / silver / gold scaffold is in place

Check the file tree for models/bronze, models/silver, models/gold. Bronze should contain only sources.yml (no SQL models); silver holds stg_[source]__[table].sql views; gold holds dim_/fct_ models with Iceberg config.

Pass: all three folders exist and follow the naming pattern.

8.A full build runs clean from the IDE

From the Cloud IDE command bar, on his scratch branch:

dbt build --select bronze silver gold

Pass: build completes with 0 errors, into his dev schema.

If it fails: an immediate connection error means the environment's warehouse credentials are expired or point at a destination he can't reach — fix the environment's connection settings before debugging any SQL. Missing-column errors mean sources.yml drifted from what actually synced — recheck against the schema tab from step 4, not memory. If table_type='iceberg' errors, the sandbox may be DuckDB-backed — drop that config and materialize a plain table.

9.Docs DAG opens

Open docs (the book icon) and have him click through the existing DAG — he'll be adding to one just like it in Session 6.

Pass: DAG renders and he can trace one model from bronze source to gold.

PART Ddbt Wizard

10.Wizard installed and authenticated

On his machine:

gcloud auth application-default login
dbt-wizard

Pass: a session starts inside the sandbox dbt project with no auth error.

If it fails: expired gcloud application-default credentials are the single most common pre-demo hiccup — re-run the login. If dbt-wizard isn't found, run the install script from the course cheat sheet first.

11.One real Wizard question, end to end

Have him ask a plain-English business question (the course's own: "Why do some stores keep showing inventory variance on Item A?") and watch the sequence run: search, describe, lineage, warehouse, then dbt_compile.

Pass: he can state the safety rule in his own words — nothing touches the warehouse until he approves the compiled preview, and approved runs land only in his own dev schema, never a shared or production one.

PART ECourse readiness

12.Course site and cheat sheet

He opens the dbt Academy site, Session 1, with the cheat sheet in a second tab. Set the expectation: Sessions 1–6 in order, at his own pace, actually completing each checkpoint — plus the two bonus deep-dives before he presents to anyone.

Pass: site loads, he knows the working order, and he knows the "if something breaks" section exists in every session.

Fast reference — the four failures to check before any live run

1. Sync not finished → bronze source tests fail: always confirm sync status in Fivetran first.   2. sources.yml drift → missing-column build errors: recheck the connector's schema tab.   3. Wizard auth expired → re-run gcloud auth application-default login before the call.   4. Connection error on dbt build → environment credentials, not the SQL.
