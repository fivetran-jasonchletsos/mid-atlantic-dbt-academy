SESSION 1 dbt Cloud Refresher: Environments, IDE, and Git
Refresher +

Goal

You've had basic dbt training before — this is a fast refresh on the specific dbt Cloud mechanics you'll lean on for demo-building: environments, the Cloud IDE, and Git-backed development, not a from-scratch tutorial.

Steps

  1. Log into dbt Cloud and open your project's IDE. Confirm you can see the file tree: models/, seeds/, macros/, tests/, and dbt_project.yml.
  2. Check your environments: a Development environment (your own IDE session, your own schema) and a Deployment environment (what a scheduled job runs against). Demos live and die by knowing which one you're looking at.
  3. Create a new branch for today's work directly from the IDE before changing anything.
  4. Run a build from the Cloud IDE command bar to confirm your connection is live:
    dbt build
  5. Open docs (the little book icon) and click through the existing DAG for whatever demo project you have open — you'll be adding to a DAG just like this one in Session 6.

Checkpoint

If something breaks

dbt build fails immediately with a connection error → your environment's warehouse credentials have likely expired or point at a destination you don't have access to; check the environment's connection settings before debugging the SQL.
SESSION 2 How Our Demos Are Structured: Bronze, Silver, Gold
Build +

Goal

Learn the specific three-layer pattern our ODI demos use — this is the shape a prospect's engineer expects to see when you walk them through the DAG.

Steps

  1. BRONZE is sources only — no SQL models. Just a sources.yml declaring exactly what Fivetran landed, with tests on _fivetran_synced and _fivetran_deleted:
    version: 2 sources: - name: shopify tables: - name: orders columns: - name: _fivetran_synced tests: [not_null]
  2. SILVER is one view per bronze table, named stg_[source]__[table].sql, using a source->renamed CTE and filtering out soft-deleted rows:
    with source as ( select * from {{ source('shopify', 'orders') }} where _fivetran_deleted = false ), renamed as ( select id as order_id, customer_id, created_at as ordered_at, total_price from source ) select * from renamed
  3. GOLD is dimensional: dim_[entity].sql and fct_[event].sql, materialized as Iceberg tables so they hold up under a live audience:
    {{ config( materialized='table', table_type='iceberg', format='parquet', partitioned_by=['order_date'] ) }} select ... from {{ ref('stg_shopify__orders') }}
  4. Scaffold this in your own sandbox project: models/{bronze,silver,gold}, then dbt build --select bronze silver gold.

Checkpoint

If something breaks

Not every demo repo uses Iceberg/Athena under the hood — some run on DuckDB against seed data standing in for the real source system. If table_type='iceberg' errors on your profile, you're likely on a DuckDB-backed demo; drop that config and materialize as a plain table instead.
SESSION 3 Fivetran → dbt: the MDLS Destination
Build +

Goal

Understand exactly how a Fivetran sync becomes queryable bronze data dbt can build on — the piece prospects always ask about.

Steps

  1. Fivetran's Managed Data Lake Service (MDLS) destination lands synced data straight into an S3 bucket + Glue Data Catalog, provisioned ahead of time (Terraform in our demo repos, or by hand for a quick sandbox).
  2. In your own Fivetran account, connect a free/sandbox source connector to an MDLS destination and let a first sync complete.
  3. In dbt Cloud, point your connection at that same Glue/Athena catalog, then write sources.yml to match exactly what landed — table names and column names must match the sync 1:1, since bronze does no renaming.
  4. Run dbt build --select silver gold against it. If it fails on missing columns, your sources.yml is out of sync with what actually landed — check the connector's schema tab in Fivetran, not your memory of it.
  5. Trigger a second Fivetran sync, then re-run the same build — this is what "live data" actually looks like in a demo: the pipeline re-runs, not just the dashboard refreshing.

Checkpoint

If something breaks

Bronze source test failures right after a sync → the sync likely hasn't finished. Always confirm sync status in Fivetran before kicking off a build — a build against a half-finished sync is a common live-demo failure.
SESSION 4 dbt Wizard: AI-Assisted Model Building
Build +

Goal

This is the differentiator prospects haven't seen anywhere else: dbt Wizard turns a plain-English business question into a compiled, previewed model without you hand-writing SQL from scratch — and without touching the warehouse until you approve what it found.

Steps

  1. Install and authenticate:
    curl -fsSL https://.../install-wizard.sh | sh gcloud auth application-default login
  2. From inside any dbt project (this works against the same project your dbt Cloud IDE points at), start a session:
    dbt-wizard
  3. Ask a real business question in plain English — not a SQL request. Try the exact one from the Protocol Console below: "Why do some stores keep showing inventory variance on Item A?"
  4. Watch the tool-call sequence: search finds candidate models, describe shows grain and columns, lineage shows what feeds it and what depends on it, warehouse samples real rows to confirm the hypothesis.
  5. When it proposes a model, it runs dbt_compile first — a preview, not a materialization. Read the preview before approving anything.
  6. Only after the preview looks right do you approve dbt_run, which materializes into your own dev schema — never straight into a shared or production schema.

Checkpoint

If something breaks

Auth errors on dbt-wizard startup → your gcloud application-default credentials have expired; re-run the login command. This is the single most common live-demo hiccup with the Wizard — check it before you're in front of anyone.
SESSION 5 CI/CD and the Demo Narrative
Build +

Goal

Understand the two ways a demo actually gets delivered, and why the models you build always map to one customer's specific pain point rather than a generic dataset.

Steps

  1. Pattern A — live warehouse. A real Fivetran sync feeds a real Athena/Snowflake/etc. destination and dbt builds against it in the room. Higher wow-factor, but depends on a live connection working on the day.
  2. Pattern B — scheduled, self-contained. Some demos run entirely on dbt-core in GitHub Actions: a workflow on a cron plus manual dispatch runs dbt deps / seed / run / test / docs generate against seed data standing in for the real source system, exports the gold-layer marts to JSON, and commits the refreshed data straight back into the repo that serves the demo frontend. No cloud credentials needed at showtime — nothing to break in front of a prospect.
  3. Know which pattern the demo you're presenting uses before you're in the room, and never mix them up mid-pitch.
  4. Remember every demo is tailored: the models and story map to the specific systems a prospect currently uses and the specific pain point in their pipeline — never present a demo as generic, always frame it around what it replaces for that buyer.

Checkpoint

If something breaks

Live demo warehouse is unreachable minutes before a call → if a Pattern-B (self-contained) version of the same demo exists, switch to it rather than troubleshooting infrastructure live.
SESSION 6 Flagship: Build a Demo Slice End-to-End
Build +

Goal

Put Sessions 1-5 together: take one new business question all the way from a live Fivetran sync to a gold-layer model, using dbt Wizard to author it.

Steps

  1. Pick (or reuse) a sandbox Fivetran connector synced to an MDLS or equivalent destination, connected to a dbt Cloud project with bronze/silver/gold scaffolded per Session 2.
  2. Confirm bronze sources.yml matches the live sync and silver staging models build clean.
  3. Pick one net-new business question relevant to the fictional company in your sandbox (e.g. "which channel's conversion is slipping this month?" — the same question in the Wizard Console below).
  4. Use dbt Wizard to search, describe, and trace lineage before writing anything, then let it compile a preview.
  5. Review the preview like you would in front of a prospect: does the grain make sense, do the numbers look plausible, is anything exposed that shouldn't be (see Bonus 1 before you screen-share this).
  6. Approve the materialization, then add it to your project's docs and commit it on a branch.

Checkpoint

If something breaks

Model compiles but the numbers look wrong → go back to the warehouse sampling step before touching SQL by hand; most "wrong number" issues are a grain mismatch (e.g. joining at the wrong level) that a quick sample would have caught.
BONUS Content Rules: Getting a Demo Booth-Ready
Deep dive +

Goal

Learn the content rules that separate an internal sandbox from something you'd actually screen-share with a prospect or show on a booth screen.

Steps

  1. Never expose real underlying table names in on-screen UI copy — use business-friendly labels in anything a prospect sees.
  2. Use generic or fictional organization names in any demo data or seed set, chosen so they don't collide with a real company that might be in the room.
  3. Every connector shown in a demo should carry a clear, per-connector deep link back into the actual Fivetran connector setup — so a technical prospect can click through and see the real configuration, not just a screenshot.
  4. Before presenting, do one pass specifically looking for anything that looks like real customer data, a real internal table name, or an internal-only Slack/Jira reference leaking into a title or comment.

Checkpoint

BONUS Troubleshooting a Live Demo
Deep dive +

Goal

The five failures that actually happen mid-demo, and the fast fix for each — memorize this before a customer call, not during one.

Steps

  1. Build kicked off before the sync finished: bronze source tests fail. Check sync status in Fivetran first, always.
  2. Iceberg partition mismatch on a gold model: usually a changed partitioned_by column after data already existed under the old partitioning. Full-refresh that one model rather than debugging in place.
  3. Athena/Glue permission error mid-demo: almost always an IAM role edge case on a newly provisioned destination — have a known-good fallback project ready rather than debugging IAM live.
  4. dbt Wizard auth expired: re-run the gcloud login before you're on the call, not during it.
  5. Warehouse totally unreachable: switch to the Pattern-B (self-contained, pre-built) version of the same demo if one exists, rather than troubleshooting infrastructure in front of a prospect.

Fivetran → dbt data flow

Fivetran sync → MDLS destination (S3 + Glue) → bronze sources.yml → silver staging views → gold Iceberg tables.

Two demo delivery patterns

Live: real sync + real warehouse, built in the room.

Self-contained: dbt-core in CI on a schedule, marts exported to JSON, zero cloud credentials at showtime.

"Sync finished but build still fails"

Double-check sources.yml table/column names against the connector's actual schema tab in Fivetran — bronze does no renaming, so any drift fails immediately.

"Wizard won't authenticate"

Re-run gcloud auth application-default login. This is the most common pre-demo hiccup — check it before you're on the call.

Before you screen-share

No real table names in UI copy, generic org names only, and every connector needs a working deep link back into its real Fivetran setup.
